# DeepSeek-V4-Flash 162B K144 REAP on 4x RTX 3090 — 2026-07-21

## Outcome

The 0xSero K144 REAP GGUF loads and runs on the private DS4 fork at 128K and
256K context. The best tested configuration is the existing one-shot
expert-parallel prefill to layer-split decode path, now with an equal
`1,1,1,1` layer split because this model has no MTP weights and ample VRAM.

Model:

`/mnt/nvme/ds4-models/DeepSeek-V4-Flash-162B-GGUF/DeepSeek-V4-Flash-Spark-Mini-Q2-REAP-ds4.gguf`

- source: `0xSero/DeepSeek-V4-Flash-162B-GGUF`
- exact size: `52,593,532,000` bytes / 48.98 GiB
- SHA-256: `e917278028d7a9e25dfc9d04bf5848375dad7573c5aeab1720d6a83714352406`
- model metadata: 163.12B parameters, 43 layers, 144 routed experts, top-6,
  three hash-routed layers, 1,048,576-token training context
- quantization: IQ2_XXS routed gate/up, Q2_K routed down, Q8_0
  shared/output/attention tensors

All runs used four RTX 3090s at the existing 220 W power limit, CUDA P2P,
`ubatch=512`, FlashAttention, no repack, and the production DS4 optimization
flags. The machine has PCIe `NODE` links and no NVLink.

## Fork compatibility work

Two small generalizations were needed to avoid penalizing or rejecting the
non-power-of-two expert count:

1. The fused CUDA MoE router now supports 144 experts / top-6. Its per-thread
   scratch length uses ceil division so the partial fifth warp lane group is
   valid. A dedicated backend test covers the K144 shape.
2. The EP-to-layer permutation now derives its block unit as the GCD of the
   real expert shard sizes. The original 256-expert model still selects 12
   MiB; K144 selects 6.75 MiB.

The K144 fused router passed 24/24 CUDA-vs-CPU reference cases across all
tested gating, normalization, bias, and scaling combinations:

```bash
build-v4-cuda/bin/test-backend-ops test -b CUDA0 -o TOPK_MOE \
  -p 'ne=\[144,22,1,1\]'
```

## Measurements

Long-context measurements use `llama-batched-bench` synthetic token IDs so
they are directly comparable with the previous full-checkpoint numbers. A
separate real chat-template sanity check is recorded below.

| context | prompt | decode | prefill | one-time relayout | clean decode | decode incl. relayout | benchmark total | observed peak VRAM |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 131,072 | 129,960 | 512 | **500.16 t/s** (259.84 s) | **2.590 s** | **31.24 t/s** | 26.83 t/s | 278.92 s | ~14,020 MiB/GPU |
| 262,144 | 260,000 | 512 | **363.97 t/s** (714.35 s) | **2.591 s** | **30.08 t/s** | 25.90 t/s | 734.12 s | ~14,818 MiB/GPU |

Load time from the NVMe copy was about 21.2-21.3 seconds for both long runs.
The reported benchmark total excludes model load; complete process time was
300.14 seconds at 128K and 755.42 seconds at 256K.

The 256K run logged one deep-context UNION-list overflow
(`3858 > cap 3840`) and correctly fell back to per-token sparse FA for that
tile. It did not fall back to dense attention and did not affect stability.

### Full 284B checkpoint comparison at the same 129,960 + 512 shape

| metric | full 284B / 256 experts | K144 REAP | change |
|---|---:|---:|---:|
| GGUF size | 80.76 GiB | 48.98 GiB | -39.4% |
| load time in the recorded run | 44.77 s | 21.22 s | -52.6% |
| EP prefill | 500.18 t/s | 500.16 t/s | effectively equal |
| device relayout | 4.546 s | 2.590 s | -43.0% |
| clean decode | 31.12 t/s | 31.24 t/s | effectively equal |
| decode including relayout | 24.25 t/s | 26.83 t/s | +10.6% |

The structural pruning does not materially reduce active-token compute: both
models still execute six same-width experts per token. Its practical wins on
this fork are model load, VRAM headroom, and the smaller one-time relayout.

### Short-context split check

Two warm direct-layer `pp512 + tg128` repetitions:

| split | warm prefill | warm decode |
|---|---:|---:|
| `1,1,1,0.85` | 661.71 t/s | 28.84 t/s |
| `1,1,1,1` | 664.10 t/s | **29.08 t/s** |

The difference is small, but equal split won and leaves plenty of headroom.

### Real chat sanity

The model was run through its embedded Jinja chat template with a Russian
single-turn multiplication question. It reasoned correctly and answered
`391`; the CLI reported 36.6 t/s short-context generation.

## Reproduce the long benchmarks

Common environment:

```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
export GGML_CUDA_P2P=1
export DSV4_EXPERT_PARALLEL=1
export DSV4_EP_TO_LAYER=1
export DSV4_CONSTANT_SHAPE=1
export DSV4_SPARSE_FA=1
export DSV4_FA_UNION=1
export DSV4_IDX_SKIP=1
export DSV4_MOE_TILE=1
export DSV4_MOE_RESIDENT=1
export DSV4_GLU_FUSE=1
export DSV4_MOE_FUSE=1
export DSV4_DECODE_FUSED_IDX=1
export DSV4_DECODE_RADIX_TOPK=1
```

128K:

```bash
build-v4-cuda/bin/llama-batched-bench \
  -m /mnt/nvme/ds4-models/DeepSeek-V4-Flash-162B-GGUF/DeepSeek-V4-Flash-Spark-Mini-Q2-REAP-ds4.gguf \
  -ngl 999 --split-mode layer --flash-attn on --no-repack \
  --ctx-size 131072 --batch-size 4096 --ubatch-size 512 \
  -t 8 --poll 100 --tensor-split 1,1,1,1 --parallel 1 \
  -npp 129960 -ntg 512 -npl 1 --output-format jsonl
```

256K: change `--ctx-size` to `262144` and use
`-npp 260000 -ntg 512`.

## Recommended server command

Use the common environment above, then:

```bash
build-v4-cuda/bin/llama-server \
  -m /mnt/nvme/ds4-models/DeepSeek-V4-Flash-162B-GGUF/DeepSeek-V4-Flash-Spark-Mini-Q2-REAP-ds4.gguf \
  -ngl 999 --split-mode layer --flash-attn on --no-repack \
  --ctx-size 262144 --batch-size 4096 --ubatch-size 512 \
  -t 8 --poll 100 --tensor-split 1,1,1,1 --parallel 1 \
  --host 0.0.0.0 --port 18080 --jinja \
  --reasoning on --reasoning-format deepseek --reasoning-budget 2048
```

The EP-to-layer switch is model-wide and one-shot. Use one active slot and a
persistent session/KV cache; it does not switch back to EP for later messages.
